# Корректная атрибуция закрытых сделок (trade_history) через orderLinkId

**Дата:** 2026-07-14
**Статус:** дизайн согласован, ожидает ревью

## Проблема

Страница «История сделок» и статистика ботов работают некорректно:

1. **Некоторые боты не фиксируют свою прибыль.** Пример — MatrixNova: подтверждено на живых данных, что у него **вообще нет строк** в `trade_history` со своим `bot_id`. Дашборд-лидерборд (`dashboard_handler.go`) использует `INNER JOIN bots b ON b.id = th.bot_id` — бот без единой такой строки просто не показывается (не «ноль», а отсутствует в списке).
2. **Сделки, совершённые ботом, помечаются как `manual`.** Подтверждено: 8 из 11 недавних `manual`/`manual_close` строк в `trade_history` — на аккаунте MatrixNova, по символам, которые он торгует.
3. **(Отдельно найдено по пути)** Статистика на карточках ботов (`MyBotCard`) сейчас жёстко захардкожена в нули — константа `mineStatsCols`/`zeroStatsCols` в `bots_handler.go` с комментарием «trade_history удалена, будет пересоздана». Это отдельный, более простой баг, задевающий вообще всех ботов, не только matrix.

### Корневая причина (1) и (2)

Модель `trade_history` и фонового синкера `ClosedPnlSyncer` спроектирована под допущение «закрытие позиции = конец цикла стратегии» (верно для grid/hedge). У matrix-бота **глобальный TP не завершает цикл** — он гасит позицию и тут же перевооружает сетку заново (`handleMatrixTPFill`, `pkg/strategy/matrix.go`). Из-за этого:

- `ClosedPnlSyncer.processClosedPnl` (шаг 2: «цикл рядом закончился по времени») не находит завершённый цикл — matrix-цикл не завершается никогда в этом сценарии.
- Шаг 3 («зомби-цикл»: открытый, но брошенный) **ошибочно матчит живой, активно торгующий matrix-цикл** — он тоже «открыт» (`ended_at IS NULL`), синкер рискует насильно закрыть здоровый цикл (`ghost_close`), провоцируя новый split-brain (симптом уже чинили этой сессией через `reviveMatrixSplitBrain`, но эта функция не спасает, если matrix-TP уже успел сбросить все `filled`-уровни в `pending` — guard на «есть filled-уровень» не проходит).
- Если ничего не подошло — шаг 4 пишет `result='manual'`, `bot_id=NULL`, `strategy_id=NULL`.

### Ключевая находка, меняющая решение

Bybit **уже возвращает** наш собственный `orderLinkId` в ответе ClosedPnl API — поле `ClosedPnl.OrderLinkId` (`pkg/trader/types.go:139`, комментарий «our custom link ID») **уже присутствует в структуре, но синкер его не читает**. При этом каждый ордер, выставленный движком стратегий, несёт linkId вида `SIS_STR-{stratID8}-...` (`stratID8` — первые 8 hex-символов UUID стратегии), из которого напрямую видно, чья это сделка, безо всякого гадания по времени.

## Решение — три независимых компонента

### A. `ClosedPnlSyncer` — атрибуция по linkId (главный фикс)

Новый **шаг 0** в `processClosedPnl`, ПЕРЕД существующими шагами 1–4:

1. Парсим `p.OrderLinkId` на префикс `SIS_STR-{stratID8}-...`.
2. Если формат совпал — ищем `strategies WHERE id::text LIKE '{stratID8}%' AND account_id = $accountID` (сверка по аккаунту — защита от теоретической коллизии 8 hex-символов). Не нашли — считаем нераспознанным (см. п. 4).
3. Нашли стратегию — классифицируем **под-паттерн** linkId и маршрутизируем:
   - **Matrix TP re-arm** (`-tp{ln|sh}-...` на стратегии `strategy_type='matrix'`) — цикл не завершается. Пишем через существующий `RecordMatrixTPProfit`/`matrix_tp_profits` (идемпотентно по `bybit_order_id`), **`ended_at` не трогаем**, зомби-логику не запускаем.
   - **Per-level matrix SL** (`-msl-...`) — это уже корректно учтено движком напрямую в `strategy_levels.realized_pnl` (`handleMatrixSLFill`). Синкер **не пишет** в `trade_history` (иначе дублирующая/фантомная строка) — только диагностический лог.
   - **Обычный TP/SL** (grid/hedge, реально завершающий цикл) — используем найденный `strategy_id` (и `cycle_num`, если он есть в linkId) напрямую вместо нынешнего нечёткого «ближайший по времени завершённый цикл». Если ещё не записано (`bybit_close_order_id` не встречается) — тот же путь `RecordStrategyTrade`, что и сейчас, просто с точным, а не угаданным контекстом.
4. **linkId не распознан** (пусто, чужой/внешний формат, реально ручная сделка с биржи не через наш движок) — падаем в **существующие шаги 2/3/4 без изменений**. Это осознанный fallback, а не удаляемый код — для настоящих ручных сделок вне системы он остаётся единственным источником данных.

Каталог всех под-паттернов linkId (TP/SL/matrix-TP с суффиксом направления `ln`/`sh`, per-level SL, обычный fill) будет точно задокументирован на этапе плана — прогрепаны все места `fmt.Sprintf("SIS_STR-...")` в `pkg/strategy` (уже частично найдены: `cycle.go:1010,1120,1873,1981,2434,2628,3728,5576`, `matrix.go:496,830,981,1279,1451`).

### B. Единый источник PnL для статистики (устраняет находку №3 и не даёт «Накоплено» и «Профит» разъезжаться)

Сейчас «Накоплено» на карточке стратегии (`GetHedgeSession`, `GetStrategyCumulativePnl`) уже суммирует **три источника**: `trade_history.net_pnl` + `strategy_levels.realized_pnl` + `matrix_tp_profits.net_pnl`. Дашборд-лидерборд и статистика карточек ботов должны использовать **тот же трёхкомпонентный набор**, а не только `trade_history`, иначе цифры на разных страницах для одного бота будут противоречить друг другу (ровно то, что происходит сейчас — лидерборд ничего не знает про `matrix_tp_profits`).

Изменения:
- `dashboard_handler.go` — «Bot leaderboard» (`GROUP BY b.id ... FROM trade_history th JOIN bots b`) — добавить агрегацию по `strategy_levels.realized_pnl` и `matrix_tp_profits.net_pnl` для стратегий этого бота, просуммировать с `trade_history`.
- `bots_handler.go` — `mineStatsCols`/`zeroStatsCols` — заменить захардкоженные нули на реальный трёхкомпонентный подсчёт по `bot_id`.
- По возможности вынести общую логику трёхкомпонентного суммирования в один переиспользуемый SQL-фрагмент/хелпер (сейчас как минимум 2 места её реализуют независимо — `GetHedgeSession` и `GetStrategyCumulativePnl` — плюс добавятся эти два), чтобы будущая правка не забыла один из потребителей.

### C. Точная подпись причины закрытия (устраняет вторую находку из брейнсторма)

`stopMatrixPair` (`matrix_engine.go`) закрывает обе позиции реальными reduce-only ордерами. Дальше это закрытие штатно долетает до движка через WS (`handlePositionCloseRetry` → `closeManualPosition` → `closePositionExternal`), который **корректно** пишет `bot_id`, но жёстко подписывает `result='manual_close'` — сделка, на 100% решённая ботом, выглядит на странице «История сделок» как ручная.

Решение: `stopMatrixPair` перед выставлением закрывающих ордеров сообщает движку стратегий, что грядущее закрытие ожидаемо и по какой причине — новый метод в `pkg/strategy` (`Engine`/`AccountRunner`), например `NotifyExpectedClose(strategyID, reason string)`, который выставляет во внутреннем состоянии соответствующего `StrategyRunner` временный флаг (`expectedCloseReason`) **с меткой времени установки**. `closePositionExternal`, обнаружив такой флаг, использует его вместо жёстко зашитого `"вручную"`/`"manual_close"` и сбрасывает флаг после использования. `bot_id` уже пишется верно — меняется только текстовая метка результата.

**Граничный случай:** если закрывающие ордера `stopMatrixPair` по какой-то причине не приведут позицию к нулю (ошибка биржи, частичное исполнение), флаг не должен «протухать» и ошибочно подписывать более позднее, не связанное с этим закрытие. Флаг живёт с коротким TTL (например, 2 минуты — сопоставимо с окном подтверждения закрытия в остальном движке) и не применяется, если `closePositionExternal` сработал позже этого окна — в этом случае используется обычная метка `"manual_close"`, как и раньше (безопасный fallback, не хуже нынешнего поведения).

## Границы и что НЕ меняется

- Схема БД не меняется — новых миграций нет, все нужные таблицы (`matrix_tp_profits`, `strategy_levels`, `trade_history`) уже существуют.
- Существующая атрибуция по времени (шаги 2/3/4 синкера) остаётся как fallback для сделок без нашего linkId — не удаляется, не переписывается, только теряет приоритет перед прямым linkId-совпадением.
- Не трогаем сам движок matrix-TP/per-level-SL (`handleMatrixTPFill`, `handleMatrixSLFill`) — только читаем то, что он уже пишет.

## Тестирование

- Юнит-тест на чистую функцию парсинга linkId: все под-паттерны (matrix-TP с `ln`/`sh`, per-level SL, обычный grid TP/SL, нераспознанный формат) → правильная классификация.
- Интеграционный тест синкера: linkId находит стратегию → живой matrix-цикл **не** зомби-закрывается, пишет в правильную таблицу (`matrix_tp_profits` для re-arm, ничего для per-level SL, `trade_history` для обычного завершения).
- Регресс-тест: существующие grid/hedge сценарии атрибуции по времени (fallback) продолжают работать как раньше — нет линкId-совпадения → старое поведение шагов 2–4 не изменилось.
- Тест на единый источник PnL (B): «Накоплено» на карточке стратегии и «Профит» в лидерборде дают одно и то же число для одного и того же бота/периода.
- Тест на пункт C: `stopMatrixPair` → результирующая строка в `trade_history` получает `result='paired_close'`, а не `manual_close`, `bot_id` корректен.
