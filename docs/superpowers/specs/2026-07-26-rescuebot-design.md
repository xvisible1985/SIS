# Дизайн: RescueBot-функция — постепенное снятие мейна за счёт накопленного PnL хеджа

Дата: 2026-07-26 (редизайн 2026-07-27: не отдельный тип бота, а доработка существующего hedge-бота)

## Контекст и проблема

Когда основная позиция («мейн») уходит в глубокую просадку (например, -20% и глубже от точки входа, ТВХ), штатный механизм системы — открыть встречную hedge-ногу и дождаться, пока комбинированный PnL пары (мейн + хедж) пересечёт порог paired-close (в т.ч. в режиме breakeven, который учитывает `accumulated_pnl` — реализованный PnL хеджа от частичных закрытий). Это работает, но требует либо полного отката цены, либо ожидания, пока суммарный результат пары наберёт нужный порог — всё это время риск на мейне остаётся полноразмерным.

**Идея (изначально называлась «RescueBot»):** пока мейн ждёт восстановления, каждый раз, когда хедж-нога фиксирует реализованную прибыль (`accumulated_pnl` растёт) и цена делает благоприятное для мейна движение, — частично закрывать мейн на объём, ровно покрывающий реализованный убыток от этого закрытия суммой из `accumulated_pnl`. Итоговый реализованный PnL по паре не меняется (потратили прибыль хеджа на закрытие части убытка мейна), но экспозиция на мейне перманентно снижается — риск уменьшается по шагам, не дожидаясь одного большого срабатывания.

## Тип бота (редизайн)

**Не новый тип бота.** Изначально планировался отдельный `bot_kind: "rescue"` (полноценный форк hedge-бота), но чтобы не плодить лишние сущности — это доработка **существующего** hedge-бота (`bot_kind: "hedge"`). Механика опциональна (тумблер `RescuePartialCloseEnabled`, по умолчанию выключен) — хедж-боты, где она не включена, ведут себя ровно как раньше, без единого изменения поведения.

**Только hedge-боты.** Matrix-боты (`bot_kind: "matrix"`), хотя тоже создают `hedge_sessions`/участвуют в paired-close, эту функцию не получают.

## Фазы

**Фаза 1 — бэкенд:** схема БД + логика частичного снятия, вызываемая из конца уже существующего `processHedgeBot` (`hedge_engine.go`). Проверяемо через прямые запросы/API без UI.

**Фаза 2 — фронтенд:** доработка существующей `HedgeBotForm.tsx` — новая секция/вкладка «Частичное закрытие» внутри неё (идея переноса блока деактивации в отдельную вкладку «Закрытие» остаётся в силе, просто внутри существующей формы, а не новой). Новый bot_kind/карточка/`BOT_KIND_META`-запись не нужны.

Фаза 2 стартует только после того, как Фаза 1 проверена и работает.

## Архитектура (бэкенд)

Никаких изменений в диспетчере `runHedgeEngine` (`hedge_engine.go:32`) не требуется — SQL-фильтр (`bot_kind IN ('hedge','matrix')`) и switch по `cfg.BotKind` остаются как есть, `bot_kind` для этой функции по-прежнему `"hedge"`.

Новая функция `checkRescuePartialClose` вызывается **в конце тела `processHedgeBot`** (после уже существующих вызовов `checkHedgeDeactivation`/`checkHedgeActivation`/`buildPairedCloseWatches`), под условием `if cfg.RescuePartialCloseEnabled`. `processHedgeBot` уже выполняется под `recoverEngine` panic guard как часть общего тик-цикла (`hedgeEngineTick`) — новый код автоматически наследует эту защиту, отдельная обёртка не нужна.

Paired-close и обычная деактивация хеджа продолжают работать **параллельно и независимо** от частичного снятия мейна — если сработают раньше (закроют обе ноги целиком), это не блокируется и не координируется с состоянием частичного снятия.

## Модель данных

Отдельного `HedgeCfg`-типа в кодовой базе нет — все виды ботов (`signal`/`hedge`/`matrix`/…) используют один общий `botCfgJSON` (`services/api-gateway/bot_engine.go:882-964`), парсится по `bot_kind`. RescueBot-поля добавляются в эту же структуру, не отдельным типом — так сделаны все существующие блоки (`Hedge*`, `Matrix*`).

`hedge_sessions.hedge_entry_at_start` (мигр. `060_hedge_sessions.sql`) уже хранит ровно то, что нужно как точка отсчёта для %-триггера — «exchange avg_entry хедж-позиции с момента первого открытия». Заполняется в `checkHedgeActivation` (`hedge_engine.go:1841-1854`) сразу же, как хедж-позиция становится видна на бирже. Отдельная колонка `hedge_entry_price` не нужна — переиспользуем `hedge_entry_at_start`.

Миграция `084_rescue_bot.sql` — только новые колонки на `hedge_sessions`:

- `main_reduced_coin NUMERIC(18, 8) NOT NULL DEFAULT 0` — накопительно за сессию, сколько объёма мейна снято частичными закрытиями (в монете).
- `main_reduced_usdt NUMERIC(18, 8) NOT NULL DEFAULT 0` — то же в USDT (по цене на момент каждого шага).
- `last_partial_close_at TIMESTAMPTZ` — для кулдауна между шагами.

Новые поля в `botCfgJSON` (`services/api-gateway/bot_engine.go`), рядом с существующим блоком `Hedge*`:

```go
// Частичное снятие мейна за счёт накопленного PnL хеджа — доработка hedge-бота
// (bot_kind остаётся "hedge"), не отдельный тип бота.
RescuePartialCloseEnabled       bool     `json:"rescue_partial_close_enabled"`
RescueTriggerPriceMovePct       *float64 `json:"rescue_trigger_price_move_pct"`   // T1: % от hedge_entry_at_start в сторону мейна
RescueTriggerPriceLevel         *float64 `json:"rescue_trigger_price_level"`      // T2: абсолютный уровень цены символа
RescueTriggerAccumulatedMinUsdt *float64 `json:"rescue_trigger_accumulated_min"`  // T3: минимальная сумма accumulated_pnl (USDT)
RescueTriggerSignal             *struct {
    Name   string                 `json:"name"`
    Params map[string]interface{} `json:"params"`
} `json:"rescue_trigger_signal"` // T4: тем же способом, что ActivationSignals — по имени сигнала, не по ID
RescueMinIntervalSec int `json:"rescue_min_interval_sec"` // кулдаун между шагами
```

`TriggerSignal` по форме сделан идентично существующему `ActivationSignals[i]` (`Name string` + `Params map[string]interface{}`) — в кодовой базе сигналы везде адресуются по имени, а не по ID (числовой/UUID `signal_id` в `webhooks_handler.go`/`jobs_handler.go` относится к другой подсистеме — внешнему приёму сигналов и job-результатам бэктеста, не к активационным сигналам ботов).

Каждый параметр — независимый тумблер (`nil`/не задан = выключен). Все включённые триггеры объединяются по «И» — шаг срабатывает только если истинны все активные условия.

## Механика шага частичного снятия

На каждом тике `processHedgeBot`, если `RescuePartialCloseEnabled`:

1. **Кулдаун:** пропускаем шаг, если `now - last_partial_close_at < MinIntervalSec`.
2. **Проверка триггеров:** вычисляем истинность каждого включённого T1–T4, объединяем по «И». Если хоть один включённый триггер ложен — не срабатываем.
3. **Расчёт объёма:** `ΔS = accumulated_pnl / |entryPrice_main − markPrice|` (направление зависит от side мейна: для лонга используется `entryPrice_main − markPrice`, для шорта — наоборот), округляем вниз до `qtyStep` символа.
4. **Ограничение по остатку:** если `ΔS ≥` текущего остатка мейна — закрываем мейн целиком этим шагом (без перелива объёма); частичное снятие для сессии считается завершённым (мейн исчерпан), хедж и paired-close продолжают жить независимо.
5. **Исполнение:** reduce-only ордер на `ΔS` по мейну.
6. **После исполнения:** `accumulated_pnl -= реализованный_убыток_от_ΔS` (в идеале уходит в 0; из-за округления по `qtyStep` может остаться небольшой остаток — переносится на следующий шаг, не обнуляется искусственно); `main_reduced_coin += ΔS`; `main_reduced_usdt += ΔS × markPrice`; `last_partial_close_at = now`.

## Обработка ошибок

- Ошибка размещения reduce-only ордера (сеть/биржа) — не трогаем `accumulated_pnl`/счётчики (транзакционность: обновляем состояние только после подтверждённого исполнения), логируем и оставляем повторную попытку следующему тику (кулдаун при неудаче не взводится).
- `checkRescuePartialClose` выполняется внутри `processHedgeBot`, которая уже под `recoverEngine` (как и другие боты в `runHedgeEngine`) — отдельной обёртки не требуется, паника одного бота не останавливает остальные.
- Гонка с paired-close/деактивацией хеджа, сработавшими на том же тике или между тиками (закрывшими обе ноги целиком) — частичное снятие мейна на следующем тике естественным образом станет no-op (мейна/сессии уже нет); отдельной блокировки не требуется.
