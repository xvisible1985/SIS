# Дизайн: RescueBot — постепенное снятие мейна за счёт накопленного PnL хеджа

Дата: 2026-07-26

## Контекст и проблема

Когда основная позиция («мейн») уходит в глубокую просадку (например, -20% и глубже от точки входа, ТВХ), штатный механизм системы — открыть встречную hedge-ногу и дождаться, пока комбинированный PnL пары (мейн + хедж) пересечёт порог paired-close (в т.ч. в режиме breakeven, который учитывает `accumulated_pnl` — реализованный PnL хеджа от частичных закрытий). Это работает, но требует либо полного отката цены, либо ожидания, пока суммарный результат пары наберёт нужный порог — всё это время риск на мейне остаётся полноразмерным.

**Идея RescueBot:** пока мейн ждёт восстановления, каждый раз, когда хедж-нога фиксирует реализованную прибыль (`accumulated_pnl` растёт) и цена делает благоприятное для мейна движение, — частично закрывать мейн на объём, ровно покрывающий реализованный убыток от этого закрытия суммой из `accumulated_pnl`. Итоговый реализованный PnL по паре не меняется (потратили прибыль хеджа на закрытие части убытка мейна), но экспозиция на мейне перманентно снижается — риск уменьшается по шагам, не дожидаясь одного большого срабатывания.

## Тип бота

Новый `bot_kind: "rescue"` — полноценный самостоятельный тип бота (не режим/тумблер существующего hedge-бота). Создаёт и ведёт хедж сам, повторяя логику активации/деактивации/paired-close hedge-бота, и добавляет поверх механику частичного снятия мейна.

## Фазы

**Фаза 1 — бэкенд:** схема БД + движок (`processRescueBot` в `hedge_engine.go`) + логика частичного снятия. Проверяемо через прямые запросы/API без UI.

**Фаза 2 — фронтенд:** `RescueBotForm.tsx` (форк `HedgeBotForm.tsx` с реструктурированными вкладками), запись в `BOT_KIND_META`/`KIND_ICONS`, карточка бота подхватывается автоматически через существующий `MyBotCard.tsx`.

Фаза 2 стартует только после того, как Фаза 1 проверена и работает.

## Архитектура (бэкенд)

`runHedgeEngine` (`hedge_engine.go:32`, тик каждые `hedgeEngineInterval`=30с) уже диспетчерит ботов по `strategy_config->>'bot_kind' IN ('hedge','matrix')`. Добавляем `'rescue'` в этот список и `case "rescue": s.processRescueBot(ctx, bot, cfg)`.

`processRescueBot` структурно повторяет `processHedgeBot` (активация хеджа, деактивация, paired-close — без изменений в этой части) и добавляет на каждом тике проверку блока частичного снятия мейна (см. «Механика шага» ниже). Как и остальные боты в этом цикле, оборачивается в `recoverEngine` panic guard, чтобы сбой одного бота не останавливал остальные.

Paired-close и обычная деактивация хеджа продолжают работать **параллельно и независимо** от частичного снятия мейна — если сработают раньше (закроют обе ноги целиком), это не блокируется и не координируется с состоянием частичного снятия.

## Модель данных

Миграция `084_rescue_bot.sql` — новые колонки на `hedge_sessions`:

- `main_reduced_coin NUMERIC NOT NULL DEFAULT 0` — накопительно за сессию, сколько объёма мейна снято частичными закрытиями (в монете).
- `main_reduced_usdt NUMERIC NOT NULL DEFAULT 0` — то же в USDT (по цене на момент каждого шага).
- `last_partial_close_at TIMESTAMPTZ` — для кулдауна между шагами.
- `hedge_entry_price NUMERIC` — цена «нулевого ордера» хеджа (момент активации хедж-ноги), точка отсчёта для %-триггера. Если эквивалентное поле уже существует в текущей структуре hedge-сессии — переиспользуется, отдельная колонка не добавляется (уточняется в начале реализации).

В `strategy_config` (JSONB) бота типа `rescue`, помимо обычных hedge-полей, — новый блок:

```go
type PartialCloseCfg struct {
    Enabled               bool
    TriggerPriceMovePct   *float64 // T1: % от hedge_entry_price в сторону мейна (положительное значение = движение в пользу мейна)
    TriggerPriceLevel     *float64 // T2: абсолютный уровень цены символа
    TriggerAccumulatedMin *float64 // T3: минимальная сумма accumulated_pnl (USDT) для срабатывания
    TriggerSignalID       *string  // T4: id прикреплённого сигнала
    MinIntervalSec        int      // кулдаун между шагами частичного закрытия
}
```

Каждый параметр — независимый тумблер (`nil`/не задан = выключен). Все включённые триггеры объединяются по «И» — шаг срабатывает только если истинны все активные условия.

## Механика шага частичного снятия

На каждом тике `processRescueBot`, если `PartialClose.Enabled`:

1. **Кулдаун:** пропускаем шаг, если `now - last_partial_close_at < MinIntervalSec`.
2. **Проверка триггеров:** вычисляем истинность каждого включённого T1–T4, объединяем по «И». Если хоть один включённый триггер ложен — не срабатываем.
3. **Расчёт объёма:** `ΔS = accumulated_pnl / |entryPrice_main − markPrice|` (направление зависит от side мейна: для лонга используется `entryPrice_main − markPrice`, для шорта — наоборот), округляем вниз до `qtyStep` символа.
4. **Ограничение по остатку:** если `ΔS ≥` текущего остатка мейна — закрываем мейн целиком этим шагом (без перелива объёма); частичное снятие для сессии считается завершённым (мейн исчерпан), хедж и paired-close продолжают жить независимо.
5. **Исполнение:** reduce-only ордер на `ΔS` по мейну.
6. **После исполнения:** `accumulated_pnl -= реализованный_убыток_от_ΔS` (в идеале уходит в 0; из-за округления по `qtyStep` может остаться небольшой остаток — переносится на следующий шаг, не обнуляется искусственно); `main_reduced_coin += ΔS`; `main_reduced_usdt += ΔS × markPrice`; `last_partial_close_at = now`.

## Обработка ошибок

- Ошибка размещения reduce-only ордера (сеть/биржа) — не трогаем `accumulated_pnl`/счётчики (транзакционность: обновляем состояние только после подтверждённого исполнения), логируем и оставляем повторную попытку следующему тику (кулдаун при неудаче не взводится).
- `processRescueBot` — как и другие боты в `runHedgeEngine`, под `recoverEngine`: паника одного бота не останавливает остальных.
- Гонка с paired-close/деактивацией хеджа, сработавшими на том же тике или между тиками (закрывшими обе ноги целиком) — частичное снятие мейна на следующем тике естественным образом станет no-op (мейна/сессии уже нет); отдельной блокировки не требуется.

## Тестирование

- Юнит-тесты расчёта `ΔS` (округление по `qtyStep`, разные side, edge-case когда `ΔS ≥` остатка).
- Юнит-тесты логики триггеров: каждый T1–T4 по отдельности, комбинации «И», кулдаун.
- Тест на то, что `accumulated_pnl`/`main_reduced_*`/`last_partial_close_at` обновляются только после успешного исполнения ордера, не до.
- `go test ./services/api-gateway/...` — регресс на существующие hedge/matrix/paired-close механики (по правилам проекта, CLAUDE.md).

## Открытые вопросы (уточняются в начале реализации, не блокируют дизайн)

- **T4 (прикреплённый сигнал):** точный механизм привязки сигнала к боту — нужно опереться на то, как это уже сделано для `signal`-типа ботов (найдены точки входа в `jobs_handler.go`/`webhooks_handler.go`, детали уточняются на месте).
- **`hedge_entry_price`:** возможно, эквивалент этого значения уже где-то вычисляется/хранится для hedge-сессии — тогда переиспользуется вместо новой колонки.
